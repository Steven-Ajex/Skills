# Handoff Prompt Writer

## 目标

把当前会话里正在进行的工作，压缩成一份**自包含（self-contained）**的交接提示词，让一个看不到原对话的新会话（新对话框、新 agent、新机器）只凭这份提示词和仓库，就能正确、高效地接着干。

默认中文输出；专业术语首次出现附英文注释；代码标识符、路径、命令、报错信息保留原文。

## 第一性原理定义

- 最小任务单元：把“会话工作状态”转写为“新会话的启动上下文”。
- 输入：当前对话（目标、决策、进展、失败尝试、用户偏好）+ 工作区客观状态（git、构建/测试结果、环境）。
- 输出：一份交接提示词（内联代码块），或 `HANDOFF.md` 文件 + 简短引导提示词。
- 完成判据（Definition of Done）：通过“冷启动测试”（见第 5 步）——零上下文的接手者只读这份提示词，就能答出目标与完成标准、当前状态、第一步做什么、哪些路不要再走、按什么原则取舍、如何确认没有破坏已完成部分；并且文中没有悬空指代、没有未经核实的“已完成”、没有密钥。

交接的本质是**有损压缩**：原对话可能有几十万 token，交接提示词只有几百到几千。质量不取决于写了多少，而取决于**留下了什么、丢掉了什么**。

## 适用边界

负责：

1. 为“换对话继续同一项工作”写交接提示词
2. 为大型、多阶段工作维护可持续更新的交接文件（交接链）
3. 采集并核实交接所需的仓库客观状态

不负责：

1. 接手之后的实际开发（交付交接提示词即结束，不要顺手继续开发）
2. 面向人类读者的会议纪要、周报、项目文档
3. 项目长期规则的维护（属于 `AGENTS.md` / `CLAUDE.md`；本技能只指出应迁移的条目）
4. 替用户决定未决问题（只记录问题、可选项和当前假设）

## 核心方法：信息价值分级（Information Triage）

判断一条信息要不要进交接提示词，只问一个问题：**新会话要重新得到它，代价有多大？**

| 级别 | 定义 | 典型内容 | 处理方式 |
|---|---|---|---|
| A 不可再生 | 只存在于对话中，仓库里找不到 | 用户意图与原话要求、偏好与禁忌、决策及理由、被否决的方案、失败尝试及原因、用户口述或粘贴的外部信息、当前假设 | **必须保留**，尽量精确；关键要求引用用户原话 |
| B 高成本可再生 | 能从仓库重新推导，但代价高 | 大型代码库的结构理解、调试得出的根因、关键代码位置、复现步骤、构建/测试命令、测试基线 | **结论 + 指针**：一句结论 + `path:line` 或命令 |
| C 低成本可再生 | 读文件、跑命令就能拿到 | 文件内容、代码 diff、完整日志、通用知识 | **只给指针**，不复制内容 |
| D 噪音 | 对后续工作没有影响 | 已被推翻且没有教训的中间方案、寒暄、重复的探索过程 | **丢弃**；若失败带来了教训，升级为 A 类“已排除路径” |

两条推论：

1. 失败信息（Negative Knowledge）价值最高、也最容易丢：新会话最大的浪费，是重走已经证伪的路。
2. 超出篇幅预算时，按 D → C → B（改成指针）的顺序裁剪，A 类最后才动。

分级细则、压缩手法和改写示例见 `references/information-triage.md`。

## 输出档位与交付形态

| 档位 | 篇幅（量级估算） | 适用场景 | 交付形态 |
|---|---|---|---|
| 轻量版（Lite） | ≤ 500 tokens | 单一小任务、状态简单，换对话只为清空上下文 | 内联提示词 |
| 标准版（Standard，默认） | 500–2000 tokens | 常规功能开发或调试，涉及若干文件与决策 | 内联提示词 |
| 完整版（Full） | 2000–5000 tokens | 大型、多阶段、多模块开发，预计还会多次交接 | `HANDOFF.md` 文件 + 3–5 行引导提示词 |

选择规则：

1. 用户指定了档位就按用户的来。
2. 未指定时默认标准版。满足任一条件则升级为完整版：跨 3 个以上模块、有多阶段计划、预计还要继续交接、存在分支/PR/CI/评审等协作状态。
3. 完整版写成文件，是因为文件可以版本管理、可以在下次交接时增量更新，引导提示词也能保持很短。文件位置优先遵循项目已有约定；没有约定时默认放在仓库根目录 `HANDOFF.md`（最显眼，新会话最容易发现），并询问用户是否纳入版本管理。

## 执行流程

### 0. 确认档位、交付形态与接手方式

信息足够就直接开始，不要为此反复提问。只有以下情况才向用户提问，并且一次问完：

1. 大型任务但不确定是否写文件、文件放在哪里
2. 工作区有未提交改动，需要决定是否先提交 WIP（Work In Progress）
3. 有阻塞后续工作的关键问题，需要用户在交接前拍板（不阻塞的问题记为“未决问题”即可）

接手方式写进提示词的“接手协议”：

- 核对后自主继续（默认）：新会话核对状态无误后，直接从“下一步 #1”开始。
- 先复述确认：新会话先复述目标与计划，等用户确认后再动手。适用于高风险改动，如数据迁移、删除数据、公共接口变更。

### 1. 采集客观状态（先查证，不凭记忆）

凭记忆写出的状态是交接失真的首要来源。动笔前先运行只读脚本：

```bash
python <本技能目录>/scripts/collect_handoff_state.py --repo . --base main
```

脚本输出分支、HEAD、与上游的差异、未提交/未跟踪文件、相对基线分支的提交与改动、stash、新增的 TODO/FIXME、项目标识文件与规则文件，以及交接前提醒。无法运行脚本时，手动执行等价命令：`git status --short`、`git branch --show-current`、`git log --oneline -n 10`、`git diff --stat HEAD`、`git stash list`。

git 之外还要确认：

1. 构建/测试最后一次运行的命令和结果，注明是本会话实际运行过的，还是推测的。不要为了交接去跑耗时很长的全量测试，除非用户要求。
2. 测试基线：哪些失败在本次改动之前就已存在。
3. 非 git 状态：数据库迁移是否已执行、服务是否在运行、临时文件、所需环境变量（只写名称，不写值）。

### 2. 回顾会话，分桶提炼

通读会话，重点看**早期的需求描述**和**中途的用户纠正**——长对话中这两处最容易被遗忘。按以下各项提炼，每条都用信息价值分级决定保留方式：

1. 目标与完成标准
2. 约束与偏好（含用户原话）
3. 进度（已验证 / 未验证 / 进行中 / 未开始 / 阻塞）
4. 关键决策（选了什么、为什么、放弃了什么、什么情况下应推翻）
5. 已排除路径（试过什么、现象、原因、结论）
6. 关键代码位置
7. 下一步
8. 未决问题与风险

### 3. 压缩与消歧

1. 叙事转状态：把“我们先……后来发现……于是……”改写为“当前状态 + 结论”。
2. 消解指代：所有“那个 bug”“上面的方案”“刚才的改法”，都换成具体名称 + 路径/commit/报错原文。
3. 标注确定度：`[已验证]`（有测试或运行证据）、`[未验证]`、`[假设]`。
4. 用指针替代内容：代码、日志、长文档改为路径、行号或命令。
5. 控制篇幅：超出预算时按 D → C → B 的顺序裁剪。

### 4. 按模板组装

使用 `references/handoff-template.md` 中对应档位的模板。模板顺序是刻意安排的：接手协议 → 目标 → 约束 → 状态快照 → 进度 → 决策 → 已排除路径 → 代码地图 → 下一步 → 未决问题。先让接手者知道“怎么开始”和“边界在哪”，再给细节。

### 5. 质量门禁：冷启动测试

假设自己是零上下文的接手者，只读这份提示词，逐一回答（任何一题答不上来，就说明还没写完）：

1. 最终目标是什么？做到什么程度算完成？
2. 现在处于什么状态？哪些是已验证的？
3. 第一步具体做什么（文件/函数/命令）？
4. 哪些事不能做？哪些方案已经证伪、不要重试？
5. 遇到模糊情况时，按什么原则取舍？
6. 怎么确认自己没有破坏已完成的部分？

然后检查：没有悬空指代、没有密钥、没有大段粘贴的代码/日志、与项目规则文件不冲突。完整清单（含阻断项）见 `references/quality-checklist.md`。

条件允许时（能派生子代理），把交接提示词交给一个无上下文的子代理，让它回答上面 6 个问题，再根据它答错或答不出的地方修补提示词。

### 6. 交付

1. 内联交付：完整提示词放在**一个**代码块中，方便一次复制；代码块外只附 1–3 行使用说明。提示词内部含有 ``` 代码块时，外层改用四个反引号。
2. 文件交付：写入 `HANDOFF.md`，再给出引导提示词代码块。
3. 交付时一并提醒：未提交或未推送的改动（如有）；建议迁移到 `AGENTS.md` / `CLAUDE.md` 的长期规则（如有）。
4. 交付后停止，不要继续做开发任务。

## 编写规则

1. **写给零上下文的聪明同事**：对方能从仓库轻易得到的不写，对方得不到的必须写。
2. **状态优先于叙事**：写“现在是什么样”，而不是“我们做了什么”。
3. **每个指代都能解析**：禁止“上面那个”“刚才的”“之前讨论的”。
4. **事实可验证**：状态声明附证据，如 commit hash、`path:line`、命令 + 预期结果。
5. **区分确定度**：已验证、未验证、假设分开标注；没跑过的代码不能写成“已完成”。
6. **约束附理由**：写明为什么，新会话才能在规则没覆盖到的情况下做出正确判断。
7. **用户原话保真**：关键需求和偏好直接引用，不要转述成更弱或更宽泛的说法。
8. **下一步可立即执行**：第一步要具体到文件、函数或命令，不写“继续完善”。
9. **指针替代内容**：代码、日志、文档都给路径或命令。只有不存在于任何文件中的关键片段才内联，更好的做法是先把它存成文件。
10. **不含秘密**：不写 token、密码、私钥、连接串；写“凭据在环境变量 `XXX` 中”。
11. **不与项目规则冲突**：`AGENTS.md` / `CLAUDE.md` 里已有的规则引用即可，不要重复，更不能写出相矛盾的指令。

## 大型软件开发的附加要求

1. **工作区处理**：交接前处理未提交改动。在临时或云端环境中，未提交、未推送的改动会随环境销毁而丢失。先征得用户同意，再提交 WIP 并推送；用户不同意时，逐个列出未提交文件及其完成度。
2. **任务看板**：按模块或阶段列出状态，而不是只写一个总体进度。
3. **接口契约**：已定下的接口、数据结构、API 签名写明位置，并标注“已冻结”或“可调整”——改动它们会影响其他模块。
4. **测试基线**：写明哪些测试原本就失败，避免新会话误以为是自己引入的，也避免它去修与任务无关的问题。
5. **环境与命令**：构建、运行、测试命令，依赖版本，所需环境变量名称，特殊启动步骤。
6. **协作状态**：分支名、PR 链接、CI 状态、未处理的评审意见。

## 交接链（多次交接）

1. 维护同一份 `HANDOFF.md`，**覆盖更新而不是追加堆叠**；“交接历史”每次交接只留一行。
2. 每次交接都重新核实上一份文档中的状态声明，防止“传话游戏”（Telephone Game）式失真；过时的条目删除或更正。
3. 已完成且稳定的工作压缩成一行摘要 + commit 引用。
4. 多次交接中反复出现、与具体任务无关的规则（构建命令、代码风格、目录约定），建议用户迁移到 `AGENTS.md` / `CLAUDE.md`。

## 常见反模式

1. 流水账：按时间复述过程，接手者读完仍不知道当前状态。
2. 悬空指代：“继续修那个问题”“按之前说的方案来”。
3. 虚报完成：写了但没运行验证过的代码被标成“已完成”。
4. 丢失负面知识：没写已排除路径，新会话重走老路。
5. 丢失用户偏好：输出语言、代码风格、禁止改动的范围在交接中消失。
6. 内容搬运：粘贴整段代码或日志，挤占新会话的上下文。
7. 模糊的下一步：“继续优化”“完善功能”。
8. 盲信上一份交接：把旧交接文档的声明原样抄过来，不重新核实。
9. 越权决策：把未决问题写成已决定。
10. 泄露秘密：把 token、密码写进提示词。
