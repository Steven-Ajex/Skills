# `handoff-prompt-writer` 技能设计说明

## 1. 需求

### 1.1 原始需求

> 设计一个编写交接提示词的 skills，用于在不同对话中接手工作。比如在大型软件开发工作中，我们希望不使用全部的上下文，需要更换对话框继续工作。

### 1.2 结构化后的需求

- 角色：为 AI 编码助手（Codex、Claude Code 等）设计一个可复用的 skill。
- 任务：当一个会话的上下文过长、需要换新对话继续时，把当前工作状态写成一份交接提示词。
- 读者：看不到原对话的新会话（AI agent），而不是人类。
- 核心约束：
  1. 新会话不继承完整上下文，交接提示词必须自包含。
  2. 篇幅要远小于原对话，但不能丢失会导致返工或出错的信息。
  3. 面向大型软件开发：多模块、多阶段、多次交接、分支/PR/CI 等协作状态。
- 成功标准：新会话只读交接提示词和仓库，就能正确接着干，不重走失败的路，不违反用户要求。
- 风格：与本仓库其他技能一致（中文、第一性原理定义、负责/不负责边界、质量门禁、模板放在 `references/`）。

## 2. 第一性原理分析

| 问题 | 结论 |
|---|---|
| 最小任务单元 | 把“会话工作状态”转写为“新会话的启动上下文” |
| 输入 | 当前对话 + 工作区客观状态 |
| 输出 | 内联交接提示词，或 `HANDOFF.md` + 引导提示词 |
| 完成判据 | 冷启动测试 6 问全部能答出，且无悬空指代、无虚报完成、无密钥 |
| 不可跳过的前置步骤 | 采集客观状态（不凭记忆）；回看早期需求和中途纠正 |
| 方法论核心 | 按“重新获取的代价”对信息分级，决定保留、改指针还是丢弃 |

交接本质上是有损压缩。压缩质量取决于取舍标准，因此技能的核心不是模板，而是信息价值分级（Information Triage）；模板只是承载形式。

## 3. 设计原则

### 3.1 以“重新获取的代价”作为唯一取舍标准

用 A/B/C/D 四级把“写什么、不写什么”变成可操作的判断，而不是依赖“感觉重要”。这同时解释了两个关键行为：

1. 失败信息（Negative Knowledge）必须保留：它只存在于对话里，丢了就会被重走。
2. 代码和日志不复制：它们在仓库里，给指针即可，把新会话的上下文留给真正的工作。

### 3.2 先查证，不凭记忆

长对话末尾，模型对早期状态的记忆最不可靠。技能要求先运行只读脚本采集 git 状态，再动笔；“已完成”必须有运行证据，否则标为“未验证”。

### 3.3 仓库是事实来源

交接文档可能过时或有误。接手协议要求新会话先核对状态，冲突时以仓库为准并报告差异，从而阻断错误在交接链中传递。

### 3.4 写给零上下文的读者

消解所有指代、约束附理由、下一步具体到文件和命令。冷启动测试把这条原则变成可检查的门禁。

### 3.5 分层记忆

项目级长期规则放在 `AGENTS.md` / `CLAUDE.md`，任务级状态放在 `HANDOFF.md`，会话级只给引导提示词。避免每次交接都重复项目规则，也避免交接文档无限膨胀。

## 4. 文件结构

| 文件 | 职责 |
|---|---|
| `SKILL.md` | 触发描述、边界、信息价值分级、档位选择、执行流程、编写规则、反模式 |
| `references/handoff-template.md` | 轻量版、标准版、完整版模板，引导提示词，接手协议写法 |
| `references/information-triage.md` | 分级细则、压缩与消歧手法、裁剪顺序、分层记忆 |
| `references/quality-checklist.md` | 交付前门禁清单，区分阻断项与建议项 |
| `references/example-handoff.md` | 大型软件开发场景的反例/正例对照 |
| `scripts/collect_handoff_state.py` | 只读采集 git 状态，输出 Markdown 快照与交接前提醒 |
| `agents/openai.yaml` | UI 元数据 |

## 5. 关键取舍（Trade-offs）

1. **只负责“写交接”，不负责“接手”**
   - 优点：边界清晰，触发准确；接手所需的行为通过提示词里的“接手协议”传递，新会话不需要安装任何技能也能正确接手。
   - 代价：接手方的质量依赖接手协议写得好不好，因此模板对接手协议给出了专门的写法要点。

2. **三档输出，而不是一个固定模板**
   - 优点：小任务不被繁重模板拖累，大任务有足够的结构。
   - 代价：需要做一次档位判断；为此给出了明确的升级条件。

3. **完整版写成文件，而不是更长的内联提示词**
   - 优点：可版本管理、可增量更新、支持多次交接，引导提示词保持很短。
   - 代价：会在仓库中留下文件；因此要求询问用户是否纳入版本管理，并在任务结束后提醒清理。

4. **脚本只覆盖 git 状态**
   - 优点：跨平台（纯 Python 标准库 + git），只读、安全、结果确定。
   - 代价：构建/测试结果、数据库迁移、运行中的服务仍需人工确认；脚本在输出末尾显式提醒这一点。

5. **交接前的 WIP 提交需征得用户同意**
   - 优点：不越权修改用户的提交历史。
   - 代价：多一次确认；但在临时/云端环境中，这一步能避免改动随环境销毁而丢失，值得。

## 6. 后续迭代建议（可选）

1. 增加 `references/receiver-protocol.md`：独立的“接手方”行为规范，供不使用本技能写交接、但需要接手的场景参考。
2. 脚本增加 `--format json`，便于编排技能或其他工具消费。
3. 按工具补充交付细节（例如 Claude Code 的 `/compact` 与本技能的配合方式、Codex 的会话恢复方式）。
4. 收集真实交接案例，补充到示例中，覆盖调试类、重构类、跨仓库类任务。
