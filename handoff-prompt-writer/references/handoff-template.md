# 交接提示词模板（Handoff Templates）

## 使用约定

1. `<...>` 是占位符，填写时连同尖括号一起替换。
2. 没有内容的小节整节删除，不要留下“无”或空标题。例外：“未提交改动”写“无”，因为“工作区干净”本身就是信息。
3. 进度标签统一使用：`[已验证]` `[未验证]` `[进行中]` `[未开始]` `[阻塞]`；推断内容标 `[假设]`。
4. 提示词内含 ``` 代码块时，外层用四个反引号包裹，保证用户一次复制完整。
5. 第一行必须让接手者明白两件事：这是一项进行中的工作；它看不到之前的对话。

---

## 模板 1：轻量版（≤ 500 tokens）

适用：单一小任务，状态简单，换对话只是为了清空上下文。

````markdown
继续一项进行中的工作。你看不到之前的对话，以下是全部必要上下文；如与仓库实际状态冲突，以仓库为准并先告诉我。

- 目标：<一句话目标>。完成标准：<可验证的条件，如某测试通过、某命令输出某结果>
- 约束：<必须遵守的要求>（原因：<为什么>）
- 当前状态：分支 `<branch>`；已改动 `<file1>`、`<file2>`；`<测试命令>` → <结果>
- 下一步：<具体到文件/函数/命令的第一个动作>
- 注意：<已证伪的方案，不要重试> / <容易踩的坑>
````

## 模板 2：标准版（500–2000 tokens，默认）

适用：常规功能开发或调试，涉及若干文件与决策。

````markdown
# 任务交接：<任务名>

你正在接手一项进行中的工作。上一个会话因上下文容量原因结束，你看不到之前的对话；下面是继续工作所需的全部信息。本文与仓库实际状态冲突时，以仓库为准。

## 0. 接手协议（先做这些，再动手）

1. 阅读：`<必读文件1>`（<为什么要读>）、`<必读文件2>`（<为什么要读>）
2. 核对状态：运行 `<命令>`，预期 `<结果>`
3. 若实际状态与本文不符：以仓库为准，先向用户报告差异，再继续
4. <核对无误后，直接从“下一步 #1”开始> 或 <先用 3–5 句话复述目标和计划，等用户确认后再动手>

## 1. 目标

- 最终目标：<要交付什么>
- 动机：<为什么要做；帮助接手者在细节上做对取舍>
- 完成标准（Definition of Done）：
  - <可验证条件 1>
  - <可验证条件 2>

## 2. 约束与偏好

- 用户要求（原话）：“<用户原话>”
- 禁止：<不能做的事>（原因：<为什么>）
- 技术约束：<语言/框架版本、依赖、兼容性要求>
- 协作约定：<分支、提交格式、输出语言等；项目规则文件中已有的只写“遵循 `AGENTS.md`”>

## 3. 当前状态快照

- 分支：`<branch>`；HEAD：`<hash> <提交说明>`；<已推送 / 领先上游 N 个提交>
- 未提交改动：<文件列表及各自完成度> / 无
- 构建/测试：`<命令>` → <结果>（<本会话实际运行 / 推测>）
- 测试基线：<哪些失败在本次改动前就存在> / 全部通过

## 4. 进度

- [已验证] <任务>（证据：<commit / 测试名>）
- [未验证] <任务>（<缺什么验证>）
- [进行中] <任务>：已完成 <部分>，停在 `<path:line>`，剩余 <内容>
- [未开始] <任务>
- [阻塞] <任务>：卡在 <原因>，需要 <什么>

## 5. 关键决策

- D1：采用 <方案 A>，而不是 <方案 B>。理由：<原因>。推翻条件：<出现什么情况时应重新考虑>
- D2：……

## 6. 已排除路径（不要重试）

- 尝试：<做了什么> → 现象：<报错原文 / 结果> → 原因：<为什么不行> → 结论：<因此改为 / 不要再>

## 7. 代码地图

- `<path:line>`：<作用，以及与本任务的关系>
- `<path>`：<作用>

## 8. 下一步

1. <立即执行：具体动作 + 目标文件/函数 + 验证方式>
2. <动作>
3. <动作>

## 9. 未决问题与风险

- Q1：<问题>。选项：<A / B>。当前假设：<暂按 X 处理>。决定人：<用户 / 实验结果>
- 风险：<可能出错的地方及防范方式>
````

### 配套引导提示词（粘贴到新对话）

````markdown
请接手 <项目名> 的 <任务名> 工作。你看不到之前的对话。
1. 先完整阅读仓库根目录的 `HANDOFF.md`，按其中“0. 接手协议”核对仓库状态；
2. 如果文档与仓库实际状态不一致，以仓库为准，先告诉我差异；
3. 然后从“下一步 #1”开始。<可选：开始前先用 3–5 句话复述目标与计划，等我确认。>
````

## 接手协议的写法要点

接手协议决定新会话的第一个动作，是交接成败的关键：

1. **必读文件要少而准**：只列与“下一步”直接相关的 1–3 个文件，并说明为什么读。不要让新会话一上来通读整个仓库。
2. **核对命令要有预期结果**：只写“运行测试”不够，要写“运行 `pnpm test --filter auth`，预期 42 通过、1 失败（`refresh.spec.ts`，为已知问题）”。
3. **冲突时以仓库为准**：交接文档可能过时或有误，仓库才是事实来源（Source of Truth）。
4. **明确是否需要等待确认**：默认核对无误后自主继续；高风险改动要求先复述、等用户确认。
