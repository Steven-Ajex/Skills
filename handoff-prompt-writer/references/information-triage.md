# 信息价值分级与压缩手法（Information Triage & Compression）

核心问题只有一个：**新会话要重新得到这条信息，代价有多大？** 代价越高，越要写进交接提示词；代价越低，越应该只给指针或直接丢掉。

## 1. 分级细则（软件开发场景）

### A 类：不可再生（必须保留，尽量精确）

这些信息只存在于对话里，新会话无论怎么读仓库都得不到。

| 内容 | 示例 | 写法要点 |
|---|---|---|
| 用户意图与原话要求 | “不要改动公共 API”“输出要中文” | 引用原话，不要改写成更弱的说法 |
| 用户中途的纠正 | “别用 localStorage 存 token” | 纠正比初始需求更重要，单独列出 |
| 决策及理由 | 选 RS256 而不是 HS256，因为多个服务要验签 | 写清选了什么、为什么、放弃了什么 |
| 被否决的方案 | 用户否决了引入 Redis | 写明谁否决、为什么 |
| 失败尝试 | `jsonwebtoken` 依赖 Node `crypto`，在 Next.js edge runtime 中报错 | 保留报错原文的关键行 |
| 外部信息 | 用户口述的业务规则、粘贴的文档或报错 | 摘录关键部分；很长就先存成文件 |
| 当前假设 | 假设所有客户端都支持 Cookie | 标 `[假设]`，写明如何验证 |

### B 类：高成本可再生（结论 + 指针）

仓库里有线索，但重新推导要花大量时间和 token。

| 内容 | 示例写法 |
|---|---|
| 代码结构理解 | “认证逻辑集中在 `packages/auth/src/`，入口是 `index.ts`；`apps/api` 只通过 `createAuthMiddleware()` 使用它” |
| 调试得出的根因 | “重复扣款的根因：`OrderService.pay()`（`src/order/service.ts:118`）在重试时没有检查幂等键” |
| 关键代码位置 | “token 签发：`packages/auth/src/sign.ts:23`” |
| 复现步骤 | “`pnpm dev` 后访问 `/checkout`，连续点击两次支付即可复现” |
| 测试基线 | “`e2e/checkout.spec.ts` 在 main 上就失败，与本任务无关” |

### C 类：低成本可再生（只给指针）

| 不要这样写 | 应该这样写 |
|---|---|
| 粘贴 80 行 `service.ts` 的代码 | “见 `src/order/service.ts:100-180`” |
| 粘贴完整测试日志 | “运行 `pnpm test order` 查看；失败的只有 `pay.spec.ts > retries`” |
| 解释 JWT 是什么 | 不写（通用知识） |
| 列出所有改过的文件 | “运行 `git diff --stat main...HEAD` 查看” |

### D 类：噪音（丢弃）

- 已被推翻、也没有带来教训的中间方案
- 寒暄、确认、重复的探索过程
- 与当前任务无关的旁支讨论

判断技巧：如果一次失败让你知道了“某条路走不通”，它就不是噪音，而是 A 类的“已排除路径”。

## 2. 压缩与消歧手法

### 2.1 叙事转状态

叙事（不要这样写）：

> 我们先尝试在中间件里直接解析 token，后来发现 Next.js 的 edge runtime 不支持 Node 的 crypto，于是改成用 jose，然后测试就过了，接下来还要处理刷新。

状态（应该这样写）：

> - [已验证] 中间件 token 解析：使用 `jose`（`apps/web/middleware.ts:12`），`pnpm test --filter web` 通过
> - 已排除：`jsonwebtoken` 依赖 Node `crypto`，Next.js edge runtime 不支持
> - [未开始] 刷新 token 流程

### 2.2 消解指代

| 悬空指代 | 可解析的写法 |
|---|---|
| “继续修那个 bug” | “修复 `pay.spec.ts > retries` 失败：重试时生成了第二笔订单” |
| “按之前说的方案来” | “按 D2：幂等键存在 `orders.idempotency_key` 唯一索引上” |
| “刚才那个报错” | “报错原文：`TypeError: crypto.createHmac is not a function`” |
| “那个文件” | “`packages/auth/src/refresh.ts`” |
| “用户说的那个要求” | “用户要求（原话）：‘刷新 token 必须放在 HttpOnly Cookie 里’” |

### 2.3 决策记录的最小格式

```text
D<n>：采用 <A>，而不是 <B>。
理由：<为什么>。
推翻条件：<出现什么情况时应重新考虑>。
```

“推翻条件”让接手者知道：这条决策在什么情况下可以挑战，什么情况下必须遵守。

### 2.4 已排除路径的最小格式

```text
尝试：<做了什么> → 现象：<报错原文关键行 / 结果> → 原因：<为什么不行> → 结论：<因此改为 / 不要再做>
```

缺少“原因”的失败记录价值很低：接手者无法判断换个条件后是否还会失败。

### 2.5 确定度标注

| 标签 | 含义 | 需要的证据 |
|---|---|---|
| `[已验证]` | 运行过并确认正确 | 测试名、命令输出、commit |
| `[未验证]` | 写完但没有运行验证 | 说明缺哪种验证 |
| `[假设]` | 推断，尚未证实 | 说明依据和验证方法 |

写了代码但没有运行测试，只能标 `[未验证]`。这是交接中最常见、也最危险的失真。

## 3. 篇幅预算与裁剪顺序

超出目标篇幅时，按以下顺序裁剪：

1. 删除 D 类
2. C 类全部改成指针
3. B 类压缩为“一句结论 + 指针”
4. 合并同类项（多条相似的已排除路径合并为一条）
5. 仍然超出时，从标准版升级为完整版（写成文件），而不是删 A 类

A 类信息一旦丢失，新会话无从找回；宁可让提示词长一些，也不要删。

## 4. 分层记忆：什么信息放在哪里

| 层级 | 载体 | 内容 | 生命周期 |
|---|---|---|---|
| 项目级 | `AGENTS.md` / `CLAUDE.md` | 构建命令、代码风格、目录约定、长期禁忌 | 跨任务长期有效 |
| 任务级 | `HANDOFF.md` | 目标、进度、决策、已排除路径、下一步 | 任务结束即可删除或归档 |
| 会话级 | 引导提示词 / 内联交接提示词 | 让新会话开始工作的最少信息 | 一次性 |

规则：

1. 项目级规则写进交接提示词时，只写“遵循 `AGENTS.md`”，不要复制内容。
2. 在交接中发现的、与具体任务无关的长期规则，建议用户迁移到项目级文件。
3. 任务完成后，提醒用户删除或归档 `HANDOFF.md`，避免下一个任务读到过时的交接文档。
